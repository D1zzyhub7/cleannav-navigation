### 清理缺陷：`kill -TERM -- -"$launch_pid"` 无效

`ros2 launch` 由非交互 shell 后台启动，**不是进程组长**（真实 PGID 是调用 shell 的），
所以 `kill -TERM -- -"$launch_pid"` 打到一个不存在的进程组，信号从未送达，脚本卡在
`wait`。同时后台作业的 **SIGINT 被设为 SIG_IGN**，`kill -INT "$launch_pid"` 也无效。

可用的收尾顺序（都按精确 PID，不用宽泛 `pkill`）：

```bash
kill -TERM <launch_pid>            # ros2 launch 收到 SIGTERM 才会优雅关停并退出
# 脚本的 trap 随即写 cleanup.json 并退出
kill -INT <每个孤儿子进程 pid>      # gzserver / rtabmap / nav2 / 容器等
```

本次按此顺序清理：launch 与脚本退出后 `cleanup.json` 记录 `rc=1`、
`gzserver_left=1`，再对 9 个孤儿 PID 发 SIGINT 全部退出。终态：0 个 gzserver /
rtabmap / nav2 / ros2 launch / rosbag 进程，端口 11750 空闲，域 190 无持有者，
`build.lock` 空闲，`rtabmap.db` 未变（`e16e672a...`），`MemAvailable` 4.83 GiB。

### 已确认并修正的实现问题

- 原代码把 3 s 计时从 Mission Service 首次 ready 开始；如果对端时钟很晚才有效，条件清除后可能立刻提交。现在独立记录总 30 s 等待和连续有效 3 s，只有时钟条件与当前运行 preflight 均有效时才累计；软阻断或 preflight 丢失会重置 3 s 计时。
- 原判断用窗口内最小 lag，早期的正常值会遮住后来超限的样本。现在每条 `/cleannav/task_status` 都重新计算最新 lag，重复 stamp 也会更新观测值。定义 `lag = /clock_at_status_receipt - TaskStatus.header.stamp`：正数表示 Mission Manager 落后 `/clock`；大于 0.25 s 软阻断。负数表示对端较快，不会造成 Gateway 提交时间戳在未来。
